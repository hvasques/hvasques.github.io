Policyholder portal

0a

The first portal at Justos built end to end by the product team: designed in Claude Design, coded with Claude Code, live 27 days after the first commit.

My role
Product manager. I wrote the front end and the API changes.
With
A product designer (design), engineering (API review, authentication, deploy)
When
August to September 2026
Tools
Claude Design, Claude Code · React, TypeScript, Vite, Tailwind

Context

Justos is a Brazilian car insurer. The customers interacts mainly with the mobile app, which also measures how they drive with telematics.

In August 2026 we started letting the policyholder and the main driver be two different people: a company that owns the car, or a parent who insures the car their child drives. The driver kept the app, The policyholder who doesn't drive was left with nothing: no place to see the policy they pay for, check a payment or download a document.

Our solution was creating a webportal for the policyholder. However, since this would change the initial engineering roadmap planning we decided to take the matter into our own hands

What it does

A web portal for policyholders who aren't the driver. They sign in with a one-time code and can:

  • see every policy they hold, and what each one still needs before it's active;
  • check coverages, payments and failed charges;
  • download the proposal and the policy;
  • follow change requests, and find their broker's contact.

Claims and changes to the policy still go through the broker or our support team. We kept v1 from having writing operations on purpose, since this was our first experience changing the backend.

How I built it

I know my way with coding, but I never deployed an entire app before. This is the process that made it work.

  • Design first, as a clickable prototype. Our product designer led the design in Claude Design while I checked each screen against what the API could return. The prototype was exported as a handoff package: 11 screens, the seven states a policy can be in, design tokens and icons.
  • Instructions that fit a beginner. The repository's instruction file tells Claude Code that a product manager is building his first app, and asks it to explain every file it creates. I read the code I shipped.
  • The stack engineers already knew. I copied the stack of our brokers' portal, because engineers would inherit this one.
  • Mock data first, then the real API. The front end ran against a mock layer for a week. I removed it once the endpoints existed.
  • API changes through pull requests. I wrote seven pull requests on the company's API with Claude Code. First there were some rounds of review with a reviewer bot, then Engineers reviewed and approved each one.
  • A decision log. Every choice that wasn't obvious went into a numbered file in the repository: 35 entries by launch.

Engineering also owned what I shouldn't: The deploy and the CI setup.

What shipped

27 daysfrom the first commit to the release
11screens, for people and companies
7pull requests on the API, all reviewed by engineering

The portal was built alongside other tasks, and it went live in early September 2026. A few weeks later engineering moved its data reads to the company's new policy model, in their own pull requests: the code was readable enough for someone else to take over.

What I learned

  • Set up review for everything, not only the risky part. The API changes went through pull requests. The front end didn't: I committed straight to the main branch, with no CI, until launch week. On the next portal every change went through a pull request from the first day.
  • The tool is fast; the judgment is still the work. Most of my time went into deciding what the portal should refuse to do, and into reading the code until I could explain it.
  • Build for the people who inherit it. Copying a stack the engineers already used is why they could change it later without asking me.
